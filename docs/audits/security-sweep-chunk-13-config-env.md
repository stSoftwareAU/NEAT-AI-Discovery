## Probe dispositions (13a)

Code is cited by symbol. The five 13a files are unchanged between the baseline and HEAD `da7c5fc` except `mod.rs` (10 doc lines removed by #2195).

- **(a) Detection thresholds — finding already filed, #2438.** `detection.rs::noise_signal_threshold`, `dominance_threshold` and `gradient_threshold` return any value that parses as `f32`. #2272 traced each hostile value to its consumer gate, `noise_signal.rs::detect_noisy_neurons` (`ratio <= threshold`), `input_sensitivity.rs::detect_dominant_inputs` (`score <= dominance_threshold`) and `input_sensitivity.rs::detect_threshold_effects` (`gradient < gradient_threshold`), and filed #2438 (`security`, `lang:rust`, `severity:low`, `confidence:high`). `NaN` and `0` fire the detector on every neuron at the maximum gain, a negative value drops every candidate as below the gain floor, and `inf` never fires. Nothing guards the value, so no guarding `file:line` is cited. The current behaviour is pinned by nine tests in `tests/issue_2272_config_small_modules.rs`, which #2438's fix must update. Not refiled.
- **(b) `log_effective_drought_mitigation_config` — three points, no finding.** (1) It logs numbers only: the nine fields are `u32`, `u64`, `f32` or the literal `"disabled"` (`drought_reset_display`, `drought_alarm_display`), so no variable's raw string reaches the log. (2) It emits at `tracing::info!`, and `observability/mod.rs::init_tracing` defaults to `warn` when `RUST_LOG` is unset, so the line is hidden by default and an operator must set `RUST_LOG=neat_ai_discovery=info` to see it. (3) `DroughtMitigationConfig::from_env` is a snapshot taken once, by the `OnceLock::get_or_init` initialiser in `lib.rs::log_version_once` on first library use, and it has no other production caller. Every accessor it calls is read live (none of the drought levers is `OnceLock`-cached), so a variable changed after that first call changes the pipeline but not the logged line, and the module doc's claim that the snapshot is "a faithful picture of what the running pipeline will use" holds only at initialisation. Doc drift reported on #2125. Not a security finding: it is a diagnostic aid.
- **Helper notes (`helpers.rs`).** `parse_env` trims surrounding whitespace and returns `None` on unparsable input, so for a float target it accepts `inf`, `-inf` and `NaN` (the root of #2438). `parse_bool_env` is true only for `1`, `true` and `yes` (case-insensitive, trimmed) and false for everything else, including `on`, `y` and `enabled`. `parse_optional_bool_env` adds `0`, `false` and `no` as `Some(false)` and returns `None` for anything else. `with_env` and the `PARSE_ENV_HELPER_TEST` variable belong to the unit tests in `helpers.rs` only, so neither has a settings row.
- **Test-quality note (`mod.rs`).** `tests::parse_bool_env_truthy_values` asserts on literal `matches!("1", "1" | "true" | "yes")` expressions, and `tests::optional_bool_parsing` re-implements the match in a local closure. Neither calls `helpers::parse_bool_env` or `helpers::parse_optional_bool_env`, so both stay green if the helpers change. No issue tracks it (`gh issue list --state all --search "optional_bool_parsing"` finds only the chunk-13 planning issues), so this record is the only trace of it. **Suggested follow-up (untracked, so recommended):** rewrite both tests to set the variable under `#[serial]` and call `helpers::parse_bool_env` / `helpers::parse_optional_bool_env`, then assert on the result, so they fail if the helpers change.
